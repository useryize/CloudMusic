## 2. 关键架构决策（ADR）

| # | 决策 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|---|
| ADR-001 | 运行形态 | **本地 Node 服务承担签名与请求代理**（Electron 仅作外壳） | RSA 私钥必须留在 Node 侧；本机 HTTP 服务顺带绕过 CORS，且同一份代码可用 `node` 直跑或打包分发（`09` §2） | ~~纯 Web 需自建 BFF~~：本方案已内置本地服务，无需外部 BFF；Tauri：Rust 侧要重写签名与 OAuth 流程，收益不抵成本 |
| ADR-002 | 状态管理 | **TanStack Query（服务端态）+ Zustand（客户端态）双轨** | 15 个页面全是"取列表→缓存→失效"，用手写 store 会重造缓存层 | Redux Toolkit：样板多；单一 Zustand：要自己实现缓存/重试/失效 |
| ADR-003 | 播放内核 | **`HTMLAudioElement` + 单个 `AudioContext` 做音量/淡入淡出** | 音频是 25 分钟内的普通 CDN 文件，用不上 MSE/HLS；单例便于全局接管 | Web Audio 全解码：内存与 CPU 不划算；`<video>`：语义不对 |
| ADR-004 | 样式方案 | **原生 CSS Modules + CSS Variables**，token 直出设计稿色值 | 设计稿已定死 11 个色值、9 级字阶，Tailwind 的原子类反而要二次映射 | Tailwind：可读性换配置量；styled-components：运行时开销 |
| ADR-005 | 长列表 | **`@tanstack/react-virtual` 定高虚拟滚动** | 行高固定 44/48/52 三档，滚动 1000 首不掉帧 | 分页加载：歌单动辄上千首，翻页体验差 |

> 运行形态在 v1.1 已收敛为「本地 Node 服务 + 可选外壳」，不再是「Electron 专属」。ADR-001 的约束本质没变——**私钥不能进浏览器**——只是承载它的进程从 Electron 主进程换成了独立的 service 进程。

## 4. 进程模型与安全边界

> **本节已被 `09` 取代**（见 `09` §5 路由表、§6 本地鉴权）。
> 以下内容保留作为历史方案与设计意图参考：它说明了「私钥为什么不能到浏览器」以及各逻辑层的职责划分，这部分依然有效；但**通道形式已从 IPC 改为本地 HTTP**，`window.api` 不再存在。
> 实现时以 `09` 为准。两者的唯一实质差异是：IPC 靠进程隔离取得安全，HTTP 靠端口 + 令牌取得安全，后者需要自己补鉴权。

```
┌──────────────────────── main（Node）────────────────────────┐
│  config：appId / privateKey / device（safeStorage 加密落盘）  │
│  signer：RSA-SHA256 签名                                     │
│  apiProxy：拼公共参数 → 发 HTTPS → 返回 envelope             │
│  tokenStore：accessToken / refreshToken，自动续期            │
│  downloader：下载地址 → 落盘 → 进度事件                      │
└───────────────────────────┬─────────────────────────────────┘
                            │ IPC（contextBridge，白名单通道）
┌───────────────────────────┴──── renderer（Chromium）────────┐
│  React 应用：路由 / 页面 / 组件 / 播放器 UI                  │
│  拿不到 privateKey，也拿不到 accessToken 明文                 │
└──────────────────────────────────────────────────────────────┘
```

**IPC 契约（唯一对外通道，`preload` 暴露为 `window.api`）**

| 通道 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `api:request` | `{ path, biz?: object, method?: 'GET'\|'POST' }` | `{ code, msg?, data? }` | 主进程补公共参数 + 签名 + 带 token |
| `auth:qrcode` | — | `{ key, qrUrl, expiresIn }` | 生成登录二维码 |
| `auth:poll` | `{ key }` | `{ status, token? }` | 轮询扫码状态 |
| `auth:anonymous` | — | `{ token }` | 匿名登录 |
| `auth:logout` | — | `{ ok: true }` | 清 token |
| `file:download` | `{ url, name, dir }` | `{ path }` | 下载落地 |
| `app:version` | — | `{ app, electron, chrome }` | 关于页 |

**安全清单**

- `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`。
- 渲染进程 CSP：`default-src 'self'; img-src 'self' https: data:; media-src https:; connect-src 'none'`（所有出站请求走主进程）。
- `privateKey` 用 `safeStorage.encryptString` 存于 `userData/secret.bin`；首次启动引导用户粘贴，不明文落任何日志。
- 主进程对 `api:request` 的 `path` 做白名单前缀校验（只允许 `/openapi/` 开头），防被渲染进程当通用代理。

## 7. 数据层

### 7.1 签名与公共参数（服务进程）

> v1.1：签名位置从 Electron 主进程移到 `packages/core`，**代码一字未改**——它只用 `node:crypto`，本来就不依赖 Electron。路径前缀由 `src/main/` 改为 `packages/core/src/`。

公共参数固定 6 个，业务参数统一塞 `bizContent`：

```ts
// packages/core/src/signer.ts
import { createSign } from 'node:crypto'

export function sign(params: Record<string, string | number>, privateKey: string): string {
  const base = Object.keys(params)
    .filter((k) => k !== 'sign' && params[k] !== '' && params[k] != null)
    .sort()                                   // ASCII 升序
    .map((k) => `${k}=${params[k]}`)
    .join('&')
  return createSign('RSA-SHA256').update(base, 'utf8').sign(privateKey, 'base64')
}
```

```ts
// packages/core/src/client.ts（核心逻辑）
const common = {
  appId,
  accessToken: tokenStore.accessToken,
  signType: 'RSA_SHA256',
  timestamp: String(Date.now()),   // 毫秒，服务端窗口 5 分钟
  device,
}
const params = { ...common, bizContent: JSON.stringify(biz) }
params.sign = sign(params, privateKey)
```

**三条纪律**：

1. `appId`、`privateKey` 是常量，只在首次配置时写入，不随请求变化；每次变的只有 `timestamp` 与 `sign`。
2. `timestamp` 与签名必须**同一次调用内生成**，跨进程传递会导致 5 分钟窗口失效——这也是签名只能放在同时持有参数与密钥的那个进程里的原因。v1.1 后该进程是 `apps/server`，不再是 Electron 主进程。
3. `bizContent` 序列化后若走 query string 必须 URL 编码；建议统一 `POST + JSON body`，避免编码差异。

### 7.2 请求封装（前端）

> **本节已被 `09` §5.2 取代**。下面是 v1.1 的实际实现（`fetch` 替代 `window.api`）：

```ts
// packages/web/src/lib/request.ts
export async function request<T>(path: string, biz: object = {}) {
  const res = await fetch('/api/rpc', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ path, biz }),
  })
  if (res.status === 401) throw new AuthError()
  if (res.status === 409) throw new SetupRequiredError((await res.json()).missing)
  const body = await res.json()
  if (body.code !== 200) throw new ApiError(body.code, body.msg)
  return body.data as T
}
```

关键差别：`api:request` 的 IPC 通道是**双向绑定**在窗口上的，HTTP 版本则是同源 `fetch`，因此 CSP 的 `connect-src` 要从 `'none'` 放宽到 `'self'`（见 `09` §11）。

`api/playlist.ts` 只做"路径 + DTO 类型"的声明式包装，不含业务判断：

```ts
export const getPlaylistDetail = (id: number) =>
  request<PlaylistDetail>('/openapi/music/basic/playlist/detail/get/v2', { id })

export const getPlaylistTracks = (id: number, offset = 0, limit = 100) =>
  request<PlaylistTracks>('/openapi/music/basic/playlist/song/list/get/v5', { id, offset, limit })
```

### 7.3 错误归一与重试

| 情况 | 判定 | 处理 |
|---|---|---|
| 业务成功 | `code === 200` | 返回 `data` |
| 未登录 / token 失效 | 登录态类错误码 | 服务端静默续期（`token/refresh/v2`）→ 重放 1 次；仍失败 → 前端跳 `/login` |
| 参数错误 | 4xx 类 | 不重试，上报日志 + Toast「请求参数有误」 |
| 播放地址失效 | 播放失败 / `playurl` 返回异常码 | 重新解析地址并 seek 到原进度（§8.3） |
| 网络错误 / 超时 | 无响应、5xx | 指数退避重试 2 次（300ms、900ms） |
| 额度用尽 | 文档未公开错误码，按 msg 关键字匹配 | 全局限流闸门 + 提示「今日额度已用尽，明日恢复」 |

QueryClient 默认：`retry: 2`、`retryDelay: exponential`、`staleTime` 由 §7.4 的 TTL 覆盖、`refetchOnWindowFocus: false`（桌面端窗口切回不该重刷）。

### 7.4 缓存 TTL 矩阵

| 数据 | queryKey | staleTime | 说明 |
|---|---|---|---|
| 每日推荐 | `['daily', yyyyMMdd]` | 到当日 24:00 | 跨天自动失效 |
| 推荐歌单 / 最新音乐 | `['recommend','playlist']` / `['song','new']` | 10 min | |
| 歌单详情 | `['playlist', id, 'detail']` | 5 min | |
| 歌单歌曲 | `['playlist', id, 'tracks', offset]` | 5 min | 分页独立 key |
| 专辑 / 艺人详情 | `['album', id]` / `['artist', id]` | 10 min | |
| 歌词 | `['lyric', songId]` | `Infinity` | 内存常驻，切歌不重复请求 |
| 榜单列表 | `['toplist']` | 10 min | 官方每日 6:00 更新 |
| 搜索结果 | `['search', type, kw]` | 60 s | 关键词为 key |
| 评论 | `['comment', songId, sort]` | 60 s | 发布后手动 `invalidate` |
| 用户资料 / 收藏 | `['user','profile']` 等 | 5 min | 登录态变更时 `resetQueries` |
| **播放地址** | **不入缓存** | **0** | 见下 |

**播放地址三条规矩**（接口文档明确要求，违反即违规）：

1. **每次播放前现取**，不写 store、不写 localStorage、不进 Query 缓存。
2. **不转分发**：不提供"复制直链"入口，不允许多窗口共用一个 URL。
3. **失效即重取**：`audio.onerror` 或进度卡死超过 3s，判定过期，重新 `playurl` 后 `currentTime = 原进度`。

### 7.5 并发与限流

个人开发者额度按人计且每日上限未公开，所以客户端要自己收着点：

- 全局请求队列，并发上限 **3**；同一 `path + biz` 在飞行中则复用 Promise（去重）。
- 列表页首屏只取第 1 页（50~100 条），滚动到距底 200px 再取下一页。
- 批量取地址优先用 `batch/song/playurl/get`，一次最多 10 首预取；**不做整榜预取**。
- 播放行为上报（`play/data/record`）节流：进度每 15s 或暂停/切歌时上报一次，合并同曲记录。

## 8. 状态管理

### 8.1 职责划分

| 类别 | 工具 | 内容 |
|---|---|---|
| 服务端态 | TanStack Query | 所有接口返回：列表、详情、评论、歌词 |
| 客户端态 | Zustand | 播放队列、播放模式、当前曲目、进度、音量、UI（侧栏折叠、Toast） |
| 表单/临时态 | `useState` | 搜索框输入、评论草稿 |
| 持久化 | `electron-store` | 音量、播放模式、上次播放曲目、窗口尺寸 |

**禁止**：把接口数据塞进 Zustand（会出现两份真相）；把播放进度塞进 Query（每秒变更，会打爆缓存）。

### 8.2 播放器 store 形状

```ts
// src/renderer/player/store.ts
type RepeatMode = 'off' | 'all' | 'one'
type PlayStatus = 'idle' | 'resolving' | 'playing' | 'paused' | 'ended' | 'error'

interface PlayerState {
  queue: Track[]              // 播放队列（来自歌单/榜单/搜索结果）
  index: number               // 当前索引
  status: PlayStatus
  currentTime: number         // 秒，UI 用（rAF 节流到 4Hz 更新）
  duration: number
  volume: number              // 0-1
  repeat: RepeatMode
  shuffle: boolean
  quality: 'standard' | 'higher' | 'exhigh' | 'lossless'

  playQueue(tracks: Track[], startIndex: number): Promise<void>
  next(): Promise<void>
  prev(): Promise<void>
  toggle(): void
  seek(sec: number): void
  setQuality(q: PlayerState['quality']): Promise<void>
}
```

进度更新用 `requestAnimationFrame` 节流到 **4 次/秒** 写 store，避免 60fps 触发 15 个组件重渲染。

### 8.3 播放地址生命周期（状态机）

```
idle ──playQueue──▶ resolving ──url ok──▶ playing
                        │                  │  │
                        │ 失败              │  │ 过期/onerror
                        ▼                  ▼  │
                      error ◀────────── paused│
                        │                     │
                        └──重试(≤2)──▶ resolving
                                              │
                          ended ◀──曲终────────┘
```

`urlResolver.ts` 的契约：

```ts
// 永远返回一个"可用不超过 30s 感"的新地址；调用方拿到后立刻 play()
async function resolve(songId: number, quality: Quality): Promise<string>
```

切歌时序必须是：`resolve → audio.src = url → audio.play()`，三步在同一 `await` 链内完成，中间不 await 其他副作用（否则地址可能已过期）。

## 12. 错误、空态与降级

| 场景 | 表现 |
|---|---|
| 列表为空 | `Empty no-data`，文案按页面定制（「这个歌单还没有歌」） |
| 搜索无结果 | `Empty no-result` + 推荐热词（`search/hot/keyword/get/v2`） |
| 播放失败 | 底部 Toast + 自动跳下一首；连续失败 3 首暂停并提示 |
| 额度用尽 | 顶部条幅「今日接口额度已用尽」+ 只读缓存内容 |
| 未登录 | 需登录页面显示 `LoginPrompt`，不跳转打断（除 `/mine`、`/together`） |
| 无接口功能 | **不渲染**，不画禁用态（新建歌单 `+`、编辑资料、关注按钮） |
