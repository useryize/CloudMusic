## 复制整板省 chrome 的做法（效率关键）

新页面若也要「侧栏 220 + 顶栏 64 + 播放条 88」，不要从头画 ≈60 个节点：
`C("7:105", "0:1", {name, x, y})` 复制「搜索结果」整板 → `batch_read` 拿新板的 `内容区` id（复制后子节点全换新 id，不能用 `copyId+原id`）→ `D(新内容区)` → 插新内容区。一个页面铺完 chrome 只需 1 次 copy + 1 次 read。
注意：复制源要先清理干净（我先删了 7:105 的侧栏 `+` 再复制，新板就没 `+`）。

## 排版教训

- 竖向 auto-layout 容器里，同一组列表行必须再套一层 `gap:0` 的列表 frame，否则行间距会被父级 `gap`（如 18）撑开。
- 内容区高度只有 748，列表行数要按「(748-64-padding)/行高」估；每日推荐 10 行（44h）刚好占 440，剩 ~110 留白安全。
- 评论页/一起听这类「底部固定输入框」：在输入框前插一个 `height: fill_container` 的弹性占位，就能把它压到底。
- 空列表底部留白太多会被当成没做完，补 2–3 行/条把视觉重量压下来比改高度稳。

### 关键设计判断（可复用）

- **端口用 `0` 让内核分配**，不做"固定端口 + 重试"。实际端口写 `~/.cloudmusic/runtime.json`(0600)，外壳只读 port 不读 token。
- **本地 HTTP 服务的真实威胁不是"别人扫端口"，是这三类**：跨站 fetch（页面 JS 打 127.0.0.1）、DNS rebinding（Host 头伪造）、本机其他进程。捆绑 127.0.0.1 只挡局域网，挡不住本机浏览器。
- 四道护栏：Host 头正则 / `Sec-Fetch-Site` + Origin 校验 / 32 字节令牌走 HttpOnly Cookie（`?t=` → Set-Cookie → 302 到干净的 `/`）/ `path` 前缀白名单。
- **音频代理必须透传 Range**，否则 `<audio>` 拿不到 206，进度条拖不动。同时必须做 CDN 域名白名单，否则 `/api/audio?u=` 变成 SSRF（`?u=http://192.168.1.1/admin`）。
- **凭证分级**：appId / appSecret / privateKey 是应用级常量；**accessToken / refreshToken 会过期，是登录态，绝非常量**——分开对待，后者永不进仓库。
- 提交密钥的真正问题不是"值钱"，是**不可归因 + 不可撤销**：平台只验签名不验人，额度被用光无法申诉；且 git 历史追加，进了就删不掉。提交前的硬门槛是"控制台能否重置 privateKey"。
- 打包先走 **Electron 壳**，核心价值是进程生命周期免费（关窗即全退，无残留 node 占端口），体积 110-150MB 可后置优化；SEA+NSIS 约 50-70MB 但需自己处理资产解包与孤儿进程。
- `extraResources` 而非 asar：`@fastify/static` 需要真实文件路径，asar 虚拟路径读不到；`process.resourcesPath` 恰好指向这里。

### 凭证存储现状与讨论结论

- 当前页面只收集 AppID 和 PrivateKey；AppSecret、PubKey 未使用，用户 OAuth accessToken / refreshToken 尚未接入。
- 按 `09` §7.2，Node 直跑默认保存到 `~/.cloudmusic/credentials.json`，可用 `CM_DATA_DIR` 覆盖目录；`CM_APP_ID` / `CM_PRIVATE_KEY` 环境变量优先。文件是明文 JSON，创建时指定 0600；Windows 的实际保护取决于 ACL，不能认为 0600 已等同于 Windows 加密或完整权限隔离。
- 配置页提交时私钥会经过页面内存和本地 HTTP 服务；保存后读取配置状态不返回私钥，不写入浏览器持久化缓存或前端产物。
- 已向用户建议：普通配置与秘密分开存储，Windows Node 采用当前用户 DPAPI 加密，未来 Electron 使用 safeStorage，通过统一凭证存储接口适配；迁移先写密文并验证解密，再删除明文。
- **加密方案仍为建议，用户尚未要求实施，代码中没有 DPAPI / safeStorage 或明文迁移实现。** 同一用户权限下的恶意程序仍可能访问秘密，不应把系统加密描述为完全隔离。
